# Bank Lab

Two rooms in different parts of a large ROM. Switch between an amber foundry
and a blue vault while the same hero, text and click sound stay in fixed bank
zero. Each room has its own palette, floor, animated relic and FM phrase.

This is an original example for learning mapper ownership. The tiny content is
spread across a deliberately sparse 6 MiB (48 Mbit) ROM so the test really reads
beyond 4 MiB. A small game normally would not need this layout.

## Build

Copy this whole folder to a new working directory. Run these commands from the
copy, with Docker running:

```sh
docker pull ewrogers/sgdk:latest
docker run --rm ewrogers/sgdk:latest doctor
docker run --rm --mount "type=bind,source=$PWD,target=/workspace" ewrogers/sgdk:latest python3 tools/build.py release
```

PowerShell uses `${PWD}` in place of `$PWD` inside the mount argument. Docker
chooses the native Linux ARM64 or AMD64 image. To select one explicitly, add
`--platform linux/arm64` or `--platform linux/amd64` to both pull and run.

The helper builds a private bank-enabled SGDK under `out/bank-sdk/`, then builds
the game. It never edits the installed toolchain. Do not substitute the normal
`build release`: that SDK library has banking disabled and the lab rejects it.
Use `debug` for the debug library, or `clean` to remove this copy's output and
private SDK cache. `--jobs 4` sets SDK build parallelism.

The results are `out/rom.bin`, its matching `out/rom.out`, build logs and
`out/bank-layout.json`. The helper checks the mapper header, declared ROM size
and linker budgets, pads the layout, then runs SGDK's own checksum tool.
Changing the SDK, compiler or build mode invalidates the affected build cache.

## Try it

Open `out/rom.bin` as a Mega Drive cartridge in an SSF-capable emulator. For ares
on macOS, with its input already configured:

```sh
open -a ares --args --system 'Mega Drive' "$PWD/out/rom.bin"
```

| Control | Action |
| --- | --- |
| D-pad | Move the shared hero |
| A | Switch rooms, including graphics and music |
| B | Save room, position and music preference to SRAM |
| C | Load a valid record |
| Start | Toggle music |

In the usual ares mapping, J/K/L/Return are A/B/C/Start.

Check both rooms, then save, move somewhere else and switch rooms before loading.
The saved room and position should return. Music and the shared hero should
keep working, and all bank checks should stay OK. Reset and load again to test
the emulator's SRAM persistence. Do not change emulator save settings silently.

The screen checks a palette/marker CRC and a read crossing a 512 KiB boundary.
It also checks that SRAM access leaves SGDK's bank assignments unchanged. A
failed startup check displays its reason. These checks do not certify hardware
compatibility or seamless audio transitions.

## How it is arranged

| ROM bank | Content |
| --- | --- |
| 0 | Code, startup data, hero, UI, click and resource descriptors |
| 8 | Foundry palette and graphics |
| 9 | Foundry music, starting at offset `0x100` |
| 10 | Vault palette and graphics |
| 11 | Vault music |

FAR reads use CPU regions 6/7. Music owns region 3, below the SRAM aperture.
Before switching that region the lab unloads the old Z80 driver. Stage graphics
use immediate transfers or copied palette queues. Other FAR work finishes
before `SPR_update()`, and queued sprite uploads flush before any more mapping.

The single SRAM slot detects invalid records and failed readback. It does not
preserve an older save after interrupted writes. Use redundant slots for that.
The shared hero and click are original assets reused from this collection;
the stage art and two FM phrases are generated by `tools/make_assets.py`.
That optional standard-library Python script writes only to a new destination.

For the ownership rules and verified SGDK sources, see
[mapping](../../references/mapping.md) and
[audio/SRAM](../../references/audio-and-sram.md).
